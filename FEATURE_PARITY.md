## 0. Critical orientation (read first)

1. There are TWO unrelated "old desktop apps" in `D/`:
   - **Legacy Tk stack**: `dashboard.py` (Tkinter control center) + `face_bridge.py` (serial/webcam bridge, owns COM port) + `usb_watch_agent.py` / `companion_app.py` (PySide6 tray launcher) + `agent.py` (host scan) -> talks to legacy **FastAPI** `/api/...` (`D/api_client.py`).
   - **Django Companion prototype**: `django_companion/` (PySide6, ~345 lines) -> talks to **Django** `/api/v1/...` (`D/django_companion/api_client.py`).
2. The packaged exe `D\dist\HybridSecureStorageDesktop.exe` (72,400,682 bytes, built 2026-10-30 20:39) contains ONLY the Django Companion prototype: spec entry is `run_companion.py` (`D/HybridSecureStorageDesktop.spec:5`), which imports `django_companion.app` (`D/run_companion.py:3`); the PYZ table lists `django_companion`, `django_companion.api_client`, `django_companion.app` and no `dashboard`/`face_bridge`/`tkinter` entries (`D\build\HybridSecureStorageDesktop\PYZ-00.toc`). The exe therefore has no SD, PIN, face, fingerprint, or admin-management functions.
3. The legacy FastAPI server in `S/` now **hard-disables login and every session check** (HTTP 409): `S/main.py:252-257` (`require_session`), `:358-364` (`/api/auth/login`), `:503-509` (`/api/access/request`), `:1277-1293` (`/api/hardware-auth/stage|session`), `:241-249` (`reject_unbound_file_transfer`). So the legacy Tk dashboard cannot authenticate against the current `S/main.py` (every `require_admin`/`require_session` call raises). Its features below are therefore documented as *intended behavior*; none can currently work end to end.
4. The "portable app" referenced by `R/README.md:5` and by DOCS (`portable_secure_app/...`, `HSSPortable.exe`, `HSS_EXHIBITION_DEMO_MODE`) does **not exist on disk** under `R` (listing of `R` shows only `.venv311, desktop, protected_data, prototypes, server, tests`; recursive find for `portable_secure_app` to depth 4 under `C:\mini project\` returned nothing). Demo mode, DPAPI-protected face store and `demo_data.json` exist only in docs (`DOCS/hss_exhibition_demo_mode.md:10-34`), and a grep of all `D/*.py` for `HSS_EXHIBITION_DEMO_MODE|DPAPI|demo_data` found nothing.
5. Duplicate/backup files (do not port): `D/companion_app_backup.py` and `D/companion_app_new.py` are byte-identical to each other (`cmp`) and identical to the live `D/companion_app.py` after stripping CR (0 diff lines; only CRLF line endings differ). `D/face_bridge_backup.py` (40,777 B) and `D/usb_watch_agent_backup.py` (5,306 B) are genuinely different (smaller, presumably older) versions of the live files (53,647 B / 5,819 B; 687 / 199 diff lines after CR strip); I did not review their contents.

## 2. Security/quality findings in old app

1. **Hardcoded COM15 default** - `D/face_bridge.py:25` (and messages `:306,1417`); a wrong port loops forever with no UI (`:286-310`).
2. **Hardcoded loopback ports/URLs** - backend `127.0.0.1:8000` (`D/dashboard.py:33`, `D/companion_app.py:159`, `R/start_secure_system.ps1:10`); bridge enrollment API `127.0.0.1:8765` hardcoded in client (`D/dashboard.py:1650,1695`) and server (`D/face_bridge.py:1190`).
3. **Unauthenticated localhost enrollment API** - `D/face_bridge.py:1116-1194`: no auth/Origin check; the authors disabled it (`:36-38,1133-1138`) but the dashboard still calls it (`D/dashboard.py:1650,1695`), so both enroll buttons always fail with 409.
4. **Host-trusted face factor** - bridge tells firmware `FACE_VERIFIED` (`D/face_bridge.py:445`) based on host webcam match; no liveness, any process that can write the COM port can forge it (`DOCS/portable_hardware_integration_audit.md:73`).
5. **Plaintext serial protocol, spoofable events** - success text parsed with substring/equality checks (`D/face_bridge.py:1303-1324`); no nonce/MAC/replay protection (`DOCS/...audit.md:73`).
6. **Bearer token stored in plaintext file** - `.hardware_session.json` in the app directory (`D/face_bridge.py:42,899-906`; read `D/dashboard.py:34,193-203`); also `.hardware_auth_granted` marker (`D/face_bridge.py:41,56`). Any local process/user can read/forge them; dashboard trusts file `role` for first paint (`D/dashboard.py:199-220`, mitigated by `/me` re-check `:205-212`).
7. **Role trust is client-side** - admin gating is `self.current_role == "admin"` (`D/dashboard.py:1138,1625,1676,1729,2397`); role set from login payload (`:1905`). Server is the real boundary, but in this state the server rejects everything (`S/main.py:252-257`).
8. **Role selector mismatch hard-fails** - `D/django_companion/app.py:196-203` logs user out if selected view != server role (contradicts doc, see conflicts).
9. **Agent key handling** - AGENT_API_KEY stored as persistent User env var in clear (`R/install_startup_agent.ps1:18-22`); copied around env (`R/start_secure_system.ps1:8-9`, `D/companion_app.py:185-188`); `-ExecutionPolicy Bypass` in task (`R/install_startup_agent.ps1:26`). No key value read or printed by me.
10. **Hard-coded dev master secret fallback** - `S/hardware_providers.py:93` (`SECURE_SYSTEM_DEV_SECRET_KEY_2026` used when `MASTER_KEY_SEED` unset, warning printed `:97-103`); PBKDF2 only 10,000 iters (`:133`). Value is a source constant, not an environment secret.
11. **Pickle for face templates** - `pickle.load` of `face_users.pkl`/`face_encoding.pkl` (`D/face_bridge.py:10,225-238`); unsafe deserialization if file tampered; templates unencrypted on disk (`:220,241-246`). File exists at `D/face_users.pkl` (2,254 B). The face file search also falls back to `~\face_encoding.pkl` (`:66-73`).
12. **Literal-escape bugs** - `"\\n"` literal backslash-n in user-visible strings (`D/dashboard.py:1642,1662,1671,1761,1764,1785,1794,1298`) and in client path validation (`:1256` replaces two literal backslashes; `:1261-1262` check for the 2-char sequence, not real newline). Serial bug: `ser.write(b"ENROLL_FAILED\\n")` sends a literal backslash-n (`D/face_bridge.py:700`), so firmware never sees a newline.
13. **Unreachable branch / spec contradiction** - dashboard "Open" refuses non-text files (`D/dashboard.py:1059-1073`) before the temp-file/`os.startfile` code (`:1097-1108`), so the latter is dead code (source comment says to avoid it).
14. **Blocking synchronous loops in serial thread** - file list/transfer loops wait up to 300s per file in the main loop (`D/face_bridge.py:1345-1356`), blocking webcam/enrollment handling; module-level side effects (serial connect, HTTP server) run on import (`:284-310,1194`).
15. **Child process output discarded** - companion launches bridge/dashboard with `stdout/stderr=DEVNULL` (`D/companion_app.py:195-196,284-285`), `CREATE_NO_WINDOW`; failures invisible.
16. **Inconsistent multi-device policy** - watcher rejects >1 matching port (`D/usb_watch_agent.py:112-114`) while companion silently picks first (`D/companion_app.py:249-254`).
17. **CORS with credentials** on legacy server (`S/main.py:215-225`) - origins limited to localhost dev ports; low risk, noted.
18. **Docs/test drift** - `R/test_system.py` still asserts working login/access (`:56-75`) against a server that returns 409 (`S/main.py:358-364,503-509`), and a security test asserts the 409 (`R/tests/test_security_events.py:42-60`).
19. **Staged-copy architecture** - file UI operates on a server staging dir, never the physical SD (`D/dashboard.py:833,1157-1158,1190-1191`); "upload" does not reach the card.
20. **No login throttling/lockout anywhere in legacy server or client** (no counters in `S/auth.py`, `S/main.py`).
21. **Sensitive local DBs left in repo** - `R/security.db` (0 B), `S/security.db` (425,984 B), `S/security_backup_before_clear.db` (94,208 B) contain account/session data (not opened).
